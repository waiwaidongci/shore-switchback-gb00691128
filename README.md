# 港区岸电插接指引切换试验

海陵港能源调度室岸电运行组。海陵港能源调度室管理东岸、南岸两个运营区共 28 个岸电泊位。两区由独立班组值守，08:00、20:00 交班，同区各泊位同班使用同版指引。A 是现行一页式指引，B 将界面核对、接电确认与状态回填拆成顺序卡片。这里只评估指引版本对工单准时送电的影响，两版共用原有接电规程和安全检查。

导入岸电排班与工单窗口 CSV。每个作业区预先锁定配对起点与配对数，每对为连续两个 12 小时班次，每班固定六个 2 小时窗口。每行合并冻结排班、指引发布日志和计划工单计数，工单按抽签前锁定的进入接电流程时间归窗，送电确认在计划时刻后 15 分钟内记为达标。已收到且无工单的窗口填 0/0，缺报窗口留待补录。时间均为北京时间。 生成配对达标率、分配顺序、两个班次的有效分子分母、整对排除原因、每区窗口和配对覆盖率及单侧随机化 p 值，供港区调度复核、分区上线决策和班组交接。

- 值班长手工用工作簿拼接排班、屏端发布记录和送电时标，补录后容易把同一窗口算两遍。
- 按全港工单直接求平均会让繁忙班次主导结果，也会把交班时的指引残留算进版本效果。
- 班组交接报告缺少配对分母、缺报原因和随机化记录，调度室无法复核放行依据。

## 六个业务模块

1. 港区切换总览
2. 班次窗口台账
3. 洗脱与随机化运行
4. AB/BA 配对明细
5. 岸电上线复核
6. 交班报告分发

## 工作剧本

1. 11 月 9 日 07:30，能源调度室为东岸、南岸各冻结 6 对排班，区内随机抽出 3 对 AB，其余走 BA。
2. 11 月 9 日 08:00，东岸第 1 对首班切到 A，20:00 换 B，屏端发布日志记录两个版本实际生效的班次。
3. 11 月 15 日 08:15，两区完成 12 对排班共 144 个窗口。数据员导入海陵港岸电指引_20261109_窗口台账.csv 并核对区数和窗口时钟。
4. 11 月 15 日 08:30，分析员设置 2 小时洗脱、每班至少 5 张计划工单、90% 覆盖及 8 个百分点收益线，运行 400 种排班的精确枚举。
5. 11 月 15 日 08:40，班组长抽查东岸第 1 对，洗脱后保留 10/10 个窗口，A 班 8/13 达标、B 班 9/12 达标。
6. 11 月 15 日 09:00，能源调度复核两个运营区 100% 覆盖、配对平均提升 16.03 个百分点和单侧 p 值 0.0025，登记分区上线 B 的建议。
7. 11 月 15 日 09:10，导出带配对明细与复核依据的报告，安排 19:45 分发给岸电交班调度岗。

## 算法与复核

两个班次构成一个配对，各区独立随机选一半配对走 AB，其余走 BA。统一剔除各班开头的洗脱窗口。先算各有效班的达标率，再对每个有效配对的 B 减 A 等权平均。尖锐零假设下按作业区的固定配额重派顺序，缺报或工单不足的配对权重为零且保留在分配空间。小空间完整枚举，超过 50,000 个分配时用固定种子抽样 20,000 次。

缺列、重复窗口、时钟越界、发布版本不一致或分配顺序超出配额时，检查冻结排班和源日志后重传。任一区洗脱后窗口覆盖率或有效配对覆盖率低于门槛，或全试验仅覆盖一种顺序时，保留复核明细并阻断发布。 复核问题为「各区数据覆盖及两种排班顺序是否通过复核，B 的限时送电提升是否同时达到统计和业务门槛，可以分区上线、保留 A，还是需要延长试验？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `zone` | 作业区 | str |
| `planned_zones` | 计划作业区数 | int |
| `plan_start` | 该区计划起点 | str |
| `planned_pairs` | 该区计划配对数 | int |
| `pair` | 区内配对号 | int |
| `block` | 对内班次号 | int |
| `window_start` | 窗口起点（北京时间） | str |
| `sequence` | 随机排班顺序 | str |
| `guide` | 实际发布版本 | str |
| `eligible` | 提前锁定的计划工单数 | int |
| `on_time` | 15 分钟内送电工单数 | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18293`
- API 文档 `http://127.0.0.1:19293/docs`
- 数据库端口 `17793`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、MySQL 8.0 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
